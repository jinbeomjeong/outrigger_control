## 발견 사항

### [차단][R·E] RD-7 3의 "키"·"설정"이 실제 하네스 기록 꼴에서 빈 값이다. 목록 대조와 JD-1·JD-3 집합 비교가 무너진다

- 근거
  - RD-7 3(블록 66행): "키 = 그 줄·run 기록의 `key`, `id`, `case` 가운데 처음 있는 문자열(자기 것이 없으면 가장 가까운 위 객체의 것, 그것도 없으면 빈 문자열). 설정 = 기록의 `v5_setting` 값(없으면 빈 문자열)."
  - 키 이름만 센 결과(값은 읽지 않음)
    - `resume_k1/h1_d1.jsonl`, `h5_u9_v0.jsonl`, `h9_stage1.jsonl`, `h10_reuse_rerun.jsonl` 줄의 최상위에는 `key`·`id`·`case`·`v5_setting`이 없다. 키는 `job.case`(H-5·H-9·H-10) 또는 `job.d1.key`·`d1.key`(H-1)에 있고, 설정은 `job.setting`(`v5_setting` 아님)에 있다.
    - 같은 `job.case`가 `eps`·`setting`·`twin`·`offset_s`에 따라 여러 줄에 나온다.
    - 반면 `h6`·`h7`·`h8`의 `.json`과 `h9_family_F_*.json`은 `results[].key`·`results[].v5_setting`을 갖는다. u3 파일은 `results[].key`(C) 또는 `results[].id`(D, `results[].case`는 객체)를 갖고, 설정은 `results[].v5.v5_setting`에 있다.
  - 글자 그대로 읽으면 H-1·H-9 main·H-10 줄의 키·설정은 모두 빈 문자열이다. 반대로 구현자가 `job.case`·`job.setting`을 "그 기록의 것"으로 읽을 수도 있다. RD-7 3이 "키·설정·계열은 함께 맞춰야 하는 값"이라 했으므로, 두 경로가 다르게 읽으면 J11·J-P3·S-6 목록이 S-13이 된다.
  - JD-1은 "같다"를 "(묶음, 결과 파일, 키, 설정)" 집합으로 정했다(블록 89행). JD-3도 "결과 파일·키·설정 기준"이다(91행). 둘 다 위치를 빼므로, 키·설정이 빈 묶음 H-10에서는 위반 줄이 서로 구별되지 않는다.
- 실패 시나리오
  - JD-1에서 다른 H-10 줄이 위반해도 (H-10, `h10_reuse_rerun.jsonl`, "", "") 하나로 접혀 "두 시나리오와 같다"가 된다. 그러면 결정 102 멈춤 대신 결정 51의 `미달`로 읽힌다. 결론이 틀릴 수 있는 갈래다.
  - 또는 두 경로가 키를 다르게 채워 R4 재판정 전체가 S-13으로 끝난다.
- 권장 조치(control-expert, 블록 수정, sha 바뀜)
  - RD-7 3의 키·설정을 파일 꼴마다 닫는다. 예:
    - run_v5 jsonl 줄: 키 = `job.case`, H-1은 `job.d1.key`. 설정 = `job.setting`.
    - r79·family json: 키 = `results[i].key`, 설정 = `results[i].v5_setting`.
    - u3 json: 키 = `results[i].key`, 없으면 `results[i].id`. 설정 = `results[i].v5.v5_setting`.
    - 격자 run: 위 결과 항목의 키 + run 위치.
  - JD-1·JD-3의 집합 비교 단위에 위치를 넣는다: (묶음, 결과 파일, 위치[, 다리]). 키·설정은 표시용으로 둔다.
